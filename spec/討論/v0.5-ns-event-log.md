#### 1. nb 作為 emitter — MVP event 清單

nb 的主要 emitter 是 hooks (`~/.claude/hooks/modules/*.js`)。以下 event 應透過 hook-client.js 串到 ns event log：

| Event type | 觸發時機 | Hook 檔案 | 關鍵 payload |
|------------|---------|-----------|-------------|
| `session.started` | SessionStart hook 載入 context | `context-injector.js` | `{session_id, cwd, project, layer (L0-L5), depth_level, task_queue_len}` |
| `session.stopped` | Stop hook 觸發收尾 | `wrapup-guard.js` + 其他 | `{session_id, duration_ms, completed_tasks, pending_tasks, verdict}` |
| `hook.executed` | 任一 hook 完成 | hook-client.js 自身 | `{hook_name, event_name, duration_ms, has_output, decision}` |
| `hook.blocked` | hook 回 `decision: block` | guards / reviewer-enforcer | `{hook_name, reason, blocked_tool, session_id}` |
| `tool.executed` | PostToolUse | flow-observer.js | `{tool_name, duration_ms, exit_code, session_id}`（已走 SSE，可 reuse） |
| `reviewer.verdict` | reviewer agent 完成回 pass/fail/iterate | reviewer-enforcer.js | `{dispatch_id, verdict, findings_count, severity}` |
| `reflection.persisted` | reflections.jsonl 新增 entry | reflection-persist.js | `{session_id, trigger_type, actions_count, has_external_research}` |
| `rule.violated` | architecture/ rule-audit test fail | CI / local test | `{rule_path, line, violated_clause}` — **建議但 v0.5 可 defer** |
| `commit.created` | PostToolUse Bash git commit | flow-observer.js 或 new hook | `{session_id, commit_hash, files_changed, is_test_commit}` |
| `blueprint.modified` | CLAUDE.md Blueprint 段 diff | 新 hook（依 xd-80cb v0） | `{project, section, old_hash, new_hash, diff_lines}` |
| `component.scan` | component-scan.js 執行 | script / hook | `{component_type, candidates_count, eliminated_count}` |

**MVP 優先級**：session.started / session.stopped / hook.blocked / reviewer.verdict / reflection.persisted / commit.created 是第一波（p0），其他為 p1+。

**反對 over-instrumentation**：`hook.executed` 若每次 hook 都 emit → log 爆量（每 session 幾十次）。建議只在 **decision != allow** 或 **duration > 100ms** 時 emit，降噪優先。

#### 2. nb 作為 consumer — subscribe + 決策

nb 的 consume 模式偏向**批次 query**（autonomy-self-scan / component-scan）而非即時 subscribe。但部分場景需即時反應：

| Subscribe 的 event | nb 的行動 | 即時 or 批次 |
|-------------------|----------|:---:|
| `dispatch.completed` (verdict=pass) | 批次計 resolved_ratio sentinel（14d window） | 批次 |
| `dispatch.completed` (verdict=fail) | 批次計 failure rate + alert when >threshold | 批次 |
| `reviewer.verdict` (verdict=fail) | 批次累積 training 資料供 skill-judge | 批次 |
| `blueprint.modified` | **即時**觸發 structural eval（architecture.test.js） | 即時 |
| `reflection.persisted` (actions=0) | **即時** warn「空行動 = 無效反思」 | 即時 |
| `hook.blocked` (count > threshold) | 批次 alert「hook 誤報率高」 | 批次 |
| `component.scan` | 批次 query 淘汰候選餵 daily-report | 批次 |
| `rule.violated` (any) | **即時** fail CI / local commit | 即時 |

**關鍵要求**：event log 必須支援**兩種 access pattern**：
1. **Subscribe (SSE push)** — 即時場景，nb 不 polling
2. **Query (GET with filter)** — 批次場景，支援 `?type=X&since=Y&limit=Z` 分頁

若 ns 只做其中一種 → nb 用例覆蓋不全。

#### 3. Schema 關鍵欄位需求

從 hook/eval/sentinel consume 角度，event schema **必須**帶下列欄位：

```yaml
# 基礎（v0.25 protocol spec §7 要求 + nb 擴充）
schema_version: 1          # 從 protocol §7 繼承
event_type: string          # canonical enum，禁 free-form string
timestamp: number           # epoch_ms，UTC
actor_cwd: string           # 發出者 session cwd（絕對路徑）
actor_type: enum            # session-agent | task-agent | hook | script

# 相關性（nb 強制要求）
session_id: string          # 該 session 的唯一 id (hook-client.js 已有)
correlation_id: string?     # 跨 event 關聯（例：dispatch 全生命週期同一 id）
depth_level: enum?          # D0-D4，路由深度（context-injector.js 已寫 /tmp/nova-routing-level-*.txt）

# Payload（每 event_type 自訂）
payload: object             # 該 event 特定欄位

# 可追溯性（審計必需）
trigger_file: string?       # 觸發這個 event 的檔案 path（若適用）
trigger_line: number?       # 觸發的行號（若適用）
parent_event_id: string?    # 事件因果鏈的父 event id

# Consumer hint（可選但推薦）
severity: enum?             # info | warn | error | critical — 供 alert 路由
tags: string[]?             # 便於 filter（例：["dispatch", "discussion", "round-2"]）
```

**嚴格禁止**：
- ⛔ NEVER `event_type: string` 自由格式 — 必 enum，否則 consumer grep 不完全
- ⛔ NEVER payload 只塞 JSON blob 沒 typed schema — 每 event_type 必 typed（見 protocol §7）
- ⛔ NEVER 缺 `session_id` — autonomy sentinel 無法計 per-session metric
- ⛔ NEVER 缺 `timestamp` / `actor_cwd` — 基本審計需求

#### 4. Retention 偏好

nb 的具體 use case retention 需求：

| Use case | 最短 retention | 理由 |
|----------|--------------|------|
| `recent_resolved_ratio` sentinel | **14 天** | 已 hardcoded 在 autonomy-self-scan.js |
| `component-scan` `age_grace_days` | **14 天** | `config/component-lifecycle.json` |
| skill-judge training 資料累積 | **90 天** | 需要累積多個 session 的行為才有效 |
| blueprint stability metric (xd-80cb) | **7 天 minimum / 30 天 ideal** | week-0 baseline 後 4 週觀察期 |
| dispatch audit trail | **30 天** | 跨 round 討論可能跨天 |
| incident post-mortem | **180 天** | 重大事故回溯範圍 |

**nb 最低要求**：**30 天 rolling window**（覆蓋前三 use cases 大部分），不反對超過但反對低於。

**容量估算**：假設 4 session × 平均 50 events/session/day × 30 天 = 6,000 events。每筆 1KB → 6MB。對 jsonl 完全 trivial。結論：**30 天 rolling 沒成本問題，不需要 compress/archive**。

#### 5. YAGNI 刀（反對或建議延後的理由）

**結論：v0.5 event log 應該做，但範圍應比 Manager 原始想像小**。

##### 應該做的理由

1. **v0.25 protocol spec §7 已經定義 event types**，不做 event log 等於 spec 定義了沒 implementation，違反「spec 是 canonical，implementation 是 spec 的實體化」原則。
2. **blueprint stability metric** (xd-80cb week-0 baseline) 的觀察機制現在**沒有 implementation** — week-0 → week-1 的比對需要 event log 才能算 `blueprint.modified` 次數。若不做 event log，blueprint stability metric 只能手動 git log，但那不是自動化 sentinel。
3. **recent_resolved_ratio sentinel 當前 18% < floor 30%** 的根因之一可能是缺 event log → 沒辦法即時知道 dispatch complete 後 verdict 走向 → 結算時才 batch 計算偏差。
4. **reflection.persisted 品質守護** (reflect-guard.js) 現在是 synchronous check — 改 event 後可以 async 累積分析，看趨勢而非單點。

##### 建議裁切的範圍

**砍掉 v0.5**：
- ❌ 新 storage engine（SQLite / DuckDB / ClickHouse）— **全部拒絕**，用 jsonl append-only 就夠（見下方輕量方案）
- ❌ 新 dashboard UI — nc 的 menu bar 可以當 MVP reader，不需新建
- ❌ event replay 功能 — v1 再看
- ❌ cross-project event aggregation — v1 再看（v0.5 只跟單一 nova-server 端點）
- ❌ event transformation pipeline — YAGNI 到極致

**留在 v0.5**：
- ✅ `data/agent-events.jsonl` append-only 單檔
- ✅ `GET /api/sessions/:id/events?type=X&since=Y` read API（無 write API — emit 走 hook-client.js 內部 POST）
- ✅ `POST /api/events` 內部 emit endpoint（不對外 public，hook-client 專用）
- ✅ SSE `event-stream` broadcast 既有 channel extend
- ✅ MVP 7 個 event type (§1 清單 p0) — 其他 p1 defer

##### 更輕量的替代方案（若 ns 覺得 v0.5 仍太重）

**方案 L（Lighter-than-light）**：**不新建 jsonl**，直接在既有 hook log (`/tmp/hook-debug.log`) 加 structured JSON 行 + parser。零新 endpoint，零新檔案，零新 schema 管理成本。

- **優點**：絕對 YAGNI，現有 infra 複用
- **缺點**：hook-debug 檔是 rotate 的，無長期 retention；grep parse 性能差
- **適用場景**：若 Manager 覺得 v0.5 真只是「好用就好沒到要長期留」— 用 L 方案，2 週後評估是否升級 v0.5 正規版

**nb 立場**：**方案 L 不夠用**（retention 30 天 minimum + batch query 需求不匹配），直接做 v0.5 但砍功能（上面列表）。

##### 反對 ns / Manager 的可能隱藏假設

1. **隱藏假設 A**：「event log 必須 Real-time streaming 才有價值」
   - **反對**：nb 的大部分 use case 是批次 query（sentinel / scan），只需 GET with filter + 適當 buffer 即可。SSE push 只用於 blueprint.modified / reflection.persisted 兩個即時場景。**拒絕為 5% 即時需求做 100% streaming infra**。

2. **隱藏假設 B**：「event log 是 L3 孵化器訓練資料的主要來源」
   - **挑戰**：L3 孵化器的訓練資料應該是 **structured outcome**（某 task 用什麼 blueprint + 什麼 skill + 結果好壞），不是 event stream。Event log 至多是 raw material，還需要 ETL。**ns 是否預期在 event log 裡放 structured outcome？若是 → schema 需另設計，不是現在討論的 flat event**。請澄清。

3. **隱藏假設 C**：「event log 可以取代 nc 的 SSE dashboard」
   - **反對**：nc 是 UI 層 consumer，需要 typed domain events（不是 generic event stream）。Event log 是底層 infrastructure，nc 應該 consume derived views 不是 raw events。**拒絕混淆 log 層與 view 層**。
